## 2. Stack (VERIFIED IN REPOSITORY)

Next.js ^14.2 (App Router), React 18, TypeScript 5, Prisma ^5.22, `@aws-sdk/client-s3` + presigner (used for B2), `tsx`. No UI library, no validation library, no test framework, no rate-limit library, no email or payment SDK, no CI files, no `middleware.ts`. `next.config.mjs` only sets `reactStrictMode`. Local database runs from `docker-compose.yml` (PostgreSQL 16); the project rules say Supabase PostgreSQL is the active database.

## 3. Database (VERIFIED IN REPOSITORY)

`prisma/schema.prisma` has three models:

- **Product:** id, name, description, `price Float`, createdAt.
- **Purchase:** id, email, productId, `status String @default("COMPLETED")`, createdAt.
- **License:** id, email, productId, `licenseKey @unique`, status (default ACTIVE), createdAt, activatedAt, `activationStatus` (default UNACTIVATED), `machineId String?`.

Not present: Order, Payment, ProductPackage, Activation (one machine id lives on License), AuditEvent, rate-limit, email outbox, recovery tokens, invoices, customers. No indexes beyond the unique license key; email lookups are unindexed. Statuses are free strings, not enums. Prices are floating point. `seed.ts` seeds two demo products (Brahmi Tamil Grantha, Kharoshthi) with price 39.0 (currency unstated; the seed log prints `$`).

## 5. Libraries (VERIFIED IN REPOSITORY)

- **`keys.ts`:** Ed25519 sign/verify of activation tokens (`<payload>.<signature>`). A **default private key is hard-coded in the source** and used when `LICENSE_SIGNING_PRIVATE_KEY` is not set. Public key is also in source (fine). Token payload contains the license key in clear.
- **`license.ts`:** license key `NAV-XXXX-XXXX-XXXX-XXXX` from `crypto.randomBytes` (4 × 2 bytes = 64 bits of randomness); email validation; HMAC-SHA256 "purchase auth token" (72 h) whose payload contains the license key and email in readable base64; HMAC for the installer payload; backend URL resolver that falls back to a hard-coded prototype Vercel URL. **The HMAC secret has a hard-coded fallback in two places.**
- **`b2.ts`:** S3 client for Backblaze B2; presigned GET (default 900 s) with a clock-offset workaround; **package definitions hard-coded in source, including filenames, object keys and SHA-256 values for two packages**; `resolvePackageDefinition` returns the Tamil Grantha package for any unrecognised product; hard-coded fallback endpoint/region/bucket name.
- **`machine.ts` (server side):** derives a hash from hostname + arch (demo/simulated). The real machine identity is computed in the installer.
- **`prisma.ts`, `keys.ts`, `b2.ts`:** the same `.env` loading helper is copy-pasted three times.

## 6. Windows installer (VERIFIED IN REPOSITORY)

- **Two bootstrappers exist:** a C# WinForms/console program (`bootstrapper/Program.cs`, 1,106 lines, built with the .NET Framework 4 `csc.exe`, AnyCPU, manifest `asInvoker`, Windows 10/11 compatibility) and `setup.ps1` + `setup.bat`. The README mentions only the PowerShell one. This resolves discrepancy D1: **both exist; `Setup.exe` is the C# build.**
- **Flow:** read embedded payload from the end of its own file (backend URL, key, token, signature) → resolve token → derive machine ID (SHA-256 of registry MachineGuid + WMI System UUID, with a hostname fallback) → POST `/api/validate-license` → POST `/api/activation` → save the token to `C:\Program Files\NavBrahmi\activation.token` (or user profile) → download the zip from the presigned URL (`WebClient`) → SHA-256 compare against the server value → extract → copy **every `.ttf`** to the Windows fonts folder (or user fonts) → pick an MSI → `msiexec /i … /qn /norestart` → delete the temp folder in `finally`.
- **Architecture selection:** reads `PROCESSOR_ARCHITECTURE`; `amd64`, `x64` **and `arm64`** pick the amd64 MSI; anything containing `86` picks i386; **ia64 is never selected; if nothing matches it installs the first MSI found.**
- **Result reporting:** success is reported when `msiexec` exits 0, 3010 (reboot), or 1638 (already installed); there is no post-install check that the layout exists.
- **Payload protection:** the payload carries an HMAC. The verification key is a **string constant in the source and therefore inside the exe**, identical to the server's fallback. If the signature field is **absent**, the payload is accepted anyway (verification only runs when a signature is present).
- **Token handling:** the installer stores the activation token but the code contains **no Ed25519 verification**; the README's "client verifies offline" is not evidenced.
- **Backend URL rules:** must be `https://` (or localhost over http); the default is the prototype Vercel URL.
- **Signing:** `scripts/sign-exe.ps1` signs with a production PFX if provided, otherwise creates/uses a **self-signed demonstration certificate**. The server appends the payload to the exe after it was built and signed; whether the Authenticode signature still validates on the downloaded file is **NOT TESTED**.
- **Layout files:** the real client layouts are MSKLC-generated (doc 07 §11); the prototype's `Setup.exe` is our own bootstrapper, separate from the client's stock `setup.exe`.

## 10. What can be reused
